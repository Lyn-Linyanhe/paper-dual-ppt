# 提速：把时间花在内容上，不花在往返上

实测数据（2026-10-19，29 页详细版）：

| 环节 | 实测耗时 |
|---|---|
| 全量几何检查（29 页） | 6.9 秒 |
| 完整导出 PPTX（29 页） | 17.2 秒 |
| 一次模型请求（中位数） | 8.9 秒 |
| 一次模型请求（p90） | 67 秒 |
| 主会话总请求数 | 2084 次，模型时间合计约 26.5 小时 |

**结论：工具只占几十秒，真正的时间在「问了太多次模型」。** 八轮迭代里每轮都重跑了全量检查和全量导出，一共 8 次；每次修改又常常分成好几轮确认。要提速，改的是**轮次**，不是脚本。

## 1. 一次改完，不要一页一问

错误做法：改一页 → 导出 → 看图 → 再改下一页。
正确做法：把所有已知问题列成清单 → 一次改完 → 一次导出 → 一次验收。

一份清单通常包含：内容错误、对齐、页脚、导航、备注同步。它们互不冲突，没有理由分八轮。

## 2. 用生成脚本，而不是逐页手改

29 页如果逐页手写 SVG，每页都是一次长输出。实际有效的做法是写一个构建脚本：

```python
SOURCES = [1,2,3,4,...]          # 输出页 → 源页
def intro_page(root, n): ...
def rw_page(root, n): ...
DISPATCH = {4: intro_page, 5: intro_page, 6: rw_page, ...}
```

改一处逻辑，29 页同时生效。调整对齐基线只要改一个函数，不用改 29 个文件。这也是主会话实际采用的方式。

脚本仍由主代理编写和维护；不是派子代理画页面，也不是交给外部服务。

## 3. 按页增量检查

`svg_quality_checker.py` 支持单页检查：

```bash
python3 scripts/svg_quality_checker.py "<项目>" --stage page --page <页面文件> --roundtrip
```

只改 3 页就只查这 3 页；全部改完再跑一次 `final`。`--stage early` 用于前五页的中间关口。

## 4. 导出必须全量，但只导一次

导出没有按页增量，每次都是全量 17 秒——这本身不贵。真正贵的是「导出 → 转 PDF → 渲染 PNG → 看图」这条链，每轮都做一遍就是几十分钟。

规则：**只有内容和版面都定稿后才走完整渲染链**。中间检查用几何检查和文本回读，不用渲染。

## 5. 减少确认轮次

只在真正的取舍点停：用户没说清的目标、会改动结论的取舍、需要外部资源。以下不要停下来问：

- 页脚怎么写、编号怎么排、剩多少留白；
- 某页拆不拆（按密度规则自己判断）；
- 备注写多长（按 `defaults.md` 的区间）。

这些在 `defaults.md` 里已经有默认值，直接执行并在交付说明里写明即可。

## 6. 并行读取，串行写入

读论文、查资料、核原文可以并发派子代理；写文件必须串行，避免互相覆盖。

派发时给每个子代理一个**只读且边界明确**的任务：定位某几张物理页的原句、核对某个统计数字、清点图表清单。不要让子代理做方案取舍或改文件。

## 7. 别重复读已经读过的文件

同一份 PDF 页面、同一个 JSON，读一次就够。需要回查时用行号或页码定位，不要整份重读。上下文里已有的内容不要为了「确认」再读一遍。

## 8. 缓存与复用

- 已裁好的图直接复用，不要每次重新裁。
- 已确认的原文单元写进 `content.json`，后续页面直接引用 ID。
- 已算好的页脚映射表、编号约定，写成常量或 JSON，不要每页重新推导。

## 9. 一个可用的节奏

| 阶段 | 做什么 | 预期 |
|---|---|---|
| 1 | 读论文、建 content.json | 一次性，主代理亲读核心章节 |
| 2 | 写两版 plans | 一次性 |
| 3 | 写构建脚本 + 生成全部 SVG | 一次性 |
| 4 | 几何检查 + 回读 | 秒级，可多轮 |
| 5 | 定稿后导出 + 渲染 + 视觉验收 | 一次 |
| 6 | 按反馈批量修订 → 重跑 4–5 | 每轮 10 分钟内 |

按这个节奏，一篇论文的完整两版制作应该在一到两小时内完成，而不是一天。
